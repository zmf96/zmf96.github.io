2.10. 索引

  • 添加索引是成本最小的优化
    • sql加索引了吗
    • 索引是否真的生效
    • 索引是否合理
  • 一般是sql的where的条件字段或者order by、group by后面的字段需要添加索引

2.10.1. 索引不生效的场景

  • 隐式的类型转换，索引失效
  • 查询条件包含or,可能导致索引失效
  • like通配符可能导致索引失效
  • 查询条件不满足联合索引的最左匹配原则
  • 在索引列上使用mysql的内置函数
  • 对索引进行列运算（如，+、-、*、/）,索引不生效
  • 索引字段上使用（！= 或者 < >），索引可能失效
  • 索引字段上使用is null， is not null，索引可能失效
  • 左右连接，关联的字段编码格式不一样
  • 优化器选错了索引

2.10.2. 索引设计不合理

  • 删除冗余和重复索引
  • 索引一般不能超过5个
  • 索引不适合建在有大量重复数据的字段上、如性别字段
  • 适当使用覆盖索引
  • 如果需要使用force index强制走某个索引，那就需要考虑索引设计是否合理

2.11. 优化SQL

  • select具体字段，避免select *
  • 多用limit
  • 尽量用union all 代替union
  • 优化group by
  • 优化order by
  • 小表驱动大表
  • 字段类型使用合理
  • 优化litmit分页
  • exist & in的合理使用
  • join关联的表不宜过多
  • delete+in子查询不走索引
  • in元素不要过多

2.11.1. mysql慢查询的原因

  • sql没加索引
  • sql索引没生效
  • limit深分页问题
  • 单表数据量大
  • join或子查询过多
  • in元素过多（不要超过500）
  • 数据库在刷脏页
  • order by 文件排序
  • 拿不到锁
    • show processlist 查看当前语句状态
  • delete + in查询不走索引
  • group by使用临时表
  • 系统硬件或者网络资源

2.12. 避免大事务问题

  • RPC远程调用不要放到事务里面
  • 一些查询相关的操作，尽量放到事务之外
  • 事务中避免处理太多数据

2.13. 深分页问题

  • mysql的分页查询，如果数据量很大，limit 1000000, 10，这种查询会非常慢

2.13.1. 标签记录法

  • 每次查询时，先查询上一次查询的结束位置，然后从这个位置开始查询 where id > 1000000 limit 10

2.13.2. 延迟关联法

  • 先查询主键索引，然后再关联查询 where id in (select id from table where id > 1000000 limit 10)
  • eg: select acct1.id,acct1.name,acct1.balance FROM account acct1 INNER JOIN (SELECT a.id FROM account a WHERE a.create_time > '2020-09-19' limit 100000, 10) AS acct2 on acct1.id= acct2.id;

2.14. 优化程序结构

  • eg: 会员用户第一次登录，发送感谢消息
    • isFristLogin && isUserVip 比 isUserVip && isFristLogin 性能更好,后者的判断会更少

2.15. 压缩传输内容

  • 压缩传输内容，传输报文变得更小，因此传输会更快啦。10M带宽，传输10k的报文，一般比传输1M的会快

2.16. 海量数据处理，考虑使用NoSQL

  • 如果你的数据量很大，比如千万级别，亿级别或者要统计和模糊搜索，那么mysql可能就不够用了，这时候可以考虑使用NoSQL，比如mongoDB、Elasticearch、hbase等

2.17. 线程池设计要合理（协程池）

  • 关注这几个参数：核心线程、最大线程数量、阻塞队列。

    • 如果核心线程过小，则达不到很好的并行效果。
    • 如果阻塞队列不合理，不仅仅是阻塞的问题，甚至可能会OOM
    • 如果线程池不区分业务隔离，有可能核心业务被边缘业务拖垮。

  • 线程池大小设计要合理

    • 线程池大小 = CPU核数 * (1 + 平均等待时间/平均计算时间)

  • 线程池任务队列大小设计要合理

    • 队列大小 = CPU核数*(1 + 平均等待时间/平均计算时间)*2

15. 突发流量应对

  • 降级、限流、异步保证系统不挂
  • 扩容：增加从库、提升配置的方式，提升系统/组件的流量承载能力
  • 切流量：服务多机房部署，大流量来了，把流量切到其他机房
    • 全步流量经过一个机房入口，在入口下面的某个负载均衡层转到另外一个机房
      • 依赖专线
    • 域名解析，流量的最前端切换
      • 配置某些地区或者全部地方的一定百分比的流量切换到另外一个机房
        • dns缓存,切换再小时级别

16. 高并发rpc框架

  • 选择高性能的 I/O 模型, eg: 同步多路 I/O 复用模型

  • 序列化协议依据具体业务来选择。如果对性能要求不高可以选择 JSON,否则可以从 Thrift 和 Protobuf 中选择其一。

17. 50wQPS下设计未读数系统

  • 评论未读、@未读、赞未读等一对一关系的未读数可以使用上节课讲到的通用计数方案来解决；
    • 数据库 + 缓存的方案是计数系统的初级阶段，完全可以支撑中小访问量和存储量的存储服务。如果你的项目还处在初级阶段，量级还不是很大，那么你一开始可以考虑使用这种方案。
    • 通过对原生 Redis 组件的改造，我们可以极大地减小存储数据的内存开销。
    • 使用 SSD+ 内存的方案可以最终解决存储计数数据的成本问题。这个方式适用于冷热数据明显的场景，你在使用时需要考虑如何将内存中的数据做换入换出。
  • 在系统通知未读、全量用户打点等存在有限的共享存储的场景下，可以通过记录用户上次操作的时间或者偏移量，来实现未读方案；
  • 信息流未读方案最为复杂，采用的是记录用户博文数快照的方式

高并发读场景方案2: 本地缓存

缓存淘汰策略

  1. FIFO 先进先出
  2. LFU 最少使用
  3. LRU 最近最少使用
  4. W-TinyLFU
    1. W-TinyLFU 是一个结合了 LFU 和 LRU 的缓存淘汰算法，它通过引入一个计数器来记录每个 key 的访问频率，同时结合 LRU 算法来保证缓存空间的有效利用。
    2. W-TinyLFU 算法的主要思想是，如果一个 key 的访问频率在一段时间内没有下降，那么它将来被再次访问的概率也会相对较高。因此，W-TinyLFU 算法会优先保留那些访问频率高的 key，同时结合 LRU 算法来保证缓存空间的有效利用。

垂直拆分

  • 将一个数据表按照字段拆分成多个表，每个表只包含部分字段。

水平拆分

  • 水平分库：将同一个数据库中的数据按照某种规则拆分到多个数据库中。
  • 水平分表：将同一个数据库中的数据表按照某种规则拆分到多个数据表中。

  • 水平分表解决单表数据量过大的问题

  • 并发量大-——》水平分库

  • 数据量大———》水平分表

  • 范围分区

  • 哈希分区

    • 避免分区数目变化，所有数据都要重新分区： 对哈希值进行范围分区，每个数据分区接收哈希值在指定范围内的数据。
